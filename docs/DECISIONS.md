# Design decisions (approved 2026-10-28)

This file is the source of truth for the build. If code and this file disagree, fix one of them deliberately.

## Goal

An investigation agent (FastAPI) that decides which tools to use, when to process a newly uploaded document, and whether the evidence is good enough to answer. It must distinguish **missing information**, **tool failure**, **insufficient evidence** and **conflicting evidence**.

## Components

| Role | Choice |
|---|---|
| API | FastAPI + Pydantic v2 + uvicorn |
| Chunk index / retrieval | Elasticsearch 8.x: BM25 + dense kNN, fused with RRF **in Python** |
| Metadata + processing state | SQLite (stdlib `sqlite3`, WAL mode) |
| Runtime LLM | **Claude Sonnet 5.5** (`claude-sonnet-5-5`), Anthropic SDK, forced tool-use for JSON. `LLM_MODEL` / `LLM_MODEL_EXTRACT` in `.env` |
| Embeddings | `BAAI/bge-small-en-v1.5` (384-d, sentence-transformers, query instruction prefix) |
| Reranker | `BAAI/bge-reranker-base` (cross-encoder, sigmoid scores in 0..1) |
| OCR | Tesseract 5 via `pytesseract.image_to_data` (per-word confidence), Pillow preprocessing |
| PDF | PyMuPDF: text-layer triage and page rendering for OCR |
| Samples | reportlab (PDFs) + Pillow (scanned receipts) |
| Tests | pytest + FastAPI TestClient with fakes (`ScriptedLLM`, `InMemoryIndex`, `HashEmbedder`, `OverlapReranker`, `FakeOCR`) |

## Optimizations agreed (no functionality lost)

1. Planner and sufficiency judge are **one LLM call per step**; deterministic guards override it.
2. Citation verifier is **code**, not an LLM.
3. RRF fusion in Python (no paid ES feature).
4. Tesseract only; PaddleOCR is an upgrade path behind `OCREngine`.
5. No job queue in code; ingestion is a resumable SQLite state machine. Queue/workers are described in the design doc.
6. `ask_user` = persisted pause/resume (`status=NEEDS_INPUT`, `POST /investigations/{id}/continue`).
7. Uploads stored on local disk under `DATA_DIR/uploads`.
8. Session vs global visibility is one ES field (`scope`) plus an attachment filter.
9. Samples generated by `samples/make_samples.py`.
10. Hand-rolled agent loop, no framework.

## Fixes added after verification

1. **Explicit sub-questions**: every planner step returns `sub_questions` with a status each:
   `OPEN | SUPPORTED | MISSING | CONFLICTING | UNVERIFIED | INSUFFICIENT`.
2. **`process_document` has two modes**: `extract_only` (no embedding, no ES write; default for one-off evidence) and `index` (chunk → embed → ES, scope `session` or `global`).
3. **Interruption applies to investigations too**: state is persisted after every step; on startup `RUNNING` investigations become `INTERRUPTED` and can be resumed.

## Agent contract

- Actions: `search`, `get_metadata`, `process_document`, `ask_user`, `finalize`.
- Every tool returns a typed `Observation(status=OK|EMPTY|ERROR|BLOCKED|PAUSED)`. Errors are never treated as "no evidence".
- Evidence ledger: every piece of evidence (chunk, extracted field, metadata record) gets an id (`e1`, `e2`, ...). Sub-questions and the final answer may only cite ledger ids.
- Guards (deterministic):
  - `SUPPORTED` needs ≥1 existing ledger id; if all cited evidence is OCR-unverified → `UNVERIFIED`; if all cited chunks score below the rerank floor → `INSUFFICIENT`; unknown ids are dropped.
  - `CONFLICTING` needs ≥2 existing ledger ids.
  - Repeated `(tool, normalized args)` → `BLOCKED`; too many blocks → forced finalize.
  - Step budget, consecutive-failure budget → forced finalize.
  - Malformed LLM output → one repair re-prompt → safe fallback (finalize).
- Outcome (decided in code from sub-question statuses):
  `CONFLICT` > `MISSING_INFO` > `TOOL_FAILURE` / `INSUFFICIENT_EVIDENCE` (open items) > `UNVERIFIED` handling > `ANSWERED`.
  An `UNVERIFIED` sub-question gives `ANSWERED_WITH_CAVEATS` only if the planner states the verdict is robust to the uncertainty; otherwise `INSUFFICIENT_EVIDENCE`.

## Storage layout (implementation detail)

- `documents` (metadata + ingestion state, including `effective_date`, `supersedes`, `scope`, `status`, `processing` lock, `error_stage`)
- `pages` (per-page text, method native/ocr, per-word confidences)
- `chunks` (deterministic ids `{doc_id}:{page}:{idx}`)
- `investigations` (full state JSON, including ledger and step trace, saved after every step)

The ledger and step trace live inside the investigation's state JSON so each save is atomic.

## Demo domain: warranty claim (fictional brands)

Question: *Is the motor seizure of Acme Facilities' Aquaflow X200 pump (serial AQ-X200-55871) on 14 March 2026 covered under warranty?*

| Document | Role |
|---|---|
| `warranty_policy_v1.pdf` | 24 months, effective 2023-01-01 |
| `warranty_amendment_2025.pdf` | Commercial units: 12 months, effective 2025-01-01, supersedes §2 → **contradiction** |
| `service_manual_x200.pdf` | Motor seizure = failure (not wear); no purchase date |
| `customer_contract_acme.pdf` | Lease; page 3 is a **scanned page** declaring commercial use; purchase date absent → **incomplete** |
| `service_manual_x300.pdf` | **Decoy**: 36-month X300 programme |
| `receipt_hinge.png` (upload) | Purchase date 17-03-2025 with the second digit smudged → low-confidence OCR; 12 vs 17 flips the verdict → **cannot determine** |
| `receipt_nonhinge.png` (upload) | Clean date 05-03-2025, smudge on receipt number → **not covered**, answered |

Refusal query: *What is the warranty period for the Aquaflow X500?* (not in the corpus → insufficient evidence). This replaces the earlier "X300" idea, because the X300 decoy manual does state an X300 term.

## Build order

models/interfaces → samples → ingestion → retrieval → tools → agent loop → API → tests → docs.

## Change log

- 2026-10-28: LLM made provider-pluggable. `LLM_PROVIDER=anthropic` (Claude, paid) or `openai_compat`
  (any OpenAI-compatible endpoint: Groq / Gemini free tiers, OpenRouter, local Ollama). The compat client
  uses forced tool calling, auto-falls back to JSON mode, and retries 429/5xx. No agent logic changed.
- 2026-10-28: Groq retired llama-3.3-70b-versatile; default free model is now `openai/gpt-oss-120b`.
  Free-tier tokens-per-minute limits handled by client-side pacing from `x-ratelimit-*` headers,
  `reasoning_effort=low` for gpt-oss (avoids truncated tool calls), and a more compact planner prompt.
  `scripts/check_llm.py` verifies the configured model before a run.
- 2026-10-28: First live run (gpt-oss-120b) asked the user after one search and skipped the amendment and
  the scanned contract page. Added deterministic ask_user discipline: `MIN_ACTIONS_BEFORE_ASK=3`
  investigation actions first, `MAX_USER_QUESTIONS=1` per investigation (a further question finalizes and
  the refusal states what is still needed). The planner now sees a corpus catalog (title, type, product,
  effective date, OCR pages) and may run process_document(extract_only) on corpus documents.
- 2026-10-28: Added a single-file web UI (`/ui`, no build step, no external assets) for asking questions,
  answering the agent, watching steps live, and verifying citations against extracted page text (OCR
  confidence highlighted) and the original file. Supporting endpoints: `GET /investigations`,
  `GET /documents`, `GET /documents/{id}/file`, `GET /documents/{id}/pages`; `wait=false` runs investigations
  in the background so the UI can poll progress. The assignment does not require a frontend; this is for
  visibility only and the API remains the primary interface.
- 2026-10-28 (feedback round): corpus rewritten with real depth (same files: policy 3 pages, amendment 2,
  X200 manual 3, contract 3, X300 1; demo invariants kept). Section-aware chunking (chunks split at
  numbered/Schedule headings, `section` field, title+section context for embedding/reranking, multi-field
  BM25): 9 -> 40 chunks. Speed: automatic first search before the first LLM call; the planner may answer in
  its finalize call (no composer call); Groq strict JSON-schema output for gpt-oss/qwen3 (no malformed output
  or repairs); leaner planner prompt; 20 rerank candidates; models warmed up at startup. Visibility: live
  activity board (in-process; Redis with several workers), plain-language step labels and per-step model /
  tool / rate-limit timings. UI: question box in the centre with example questions, live activity and
  timeline below it, then answer and tabs; sidebar keeps history and knowledge base. Provider stays Groq
  free tier; its tokens-per-minute limit remains the main cost of multi-step investigations.
- 2026-10-28 (live test feedback): (1) relevance floor 0.2 -> 0.03, calibrated on real bge-reranker-base scores
  (correct passages for casual questions scored 0.035-0.15); (2) deterministic unknown-entity check: model
  numbers/references in the question that appear in no document force INSUFFICIENT_EVIDENCE (the live run had
  applied the X-series policy to an "X500"); (3) sub-questions can be optional (required=false): an unsupported
  optional part becomes a caveat (ANSWERED_WITH_CAVEATS) instead of blocking the answer; (4) out-of-scope
  wording for refusals with no evidence; (5) corpus: definitions, leased/unlisted-model scope, key time limits
  tables, prose spec summaries; (6) per-model rate-limit state and automatic failover to a fallback model
  (Groq quotas are per model), with a clear error when every model is exhausted.
- 2026-10-28 (second live test): false refusals traced to (1) a stale RERANK_FLOOR=0.2 line in .env overriding
  the recalibrated 0.03 - the setting is renamed RELEVANCE_FLOOR so the stale line is ignored (warning at
  startup); (2) the planner prompt truncating evidence to 400/120 characters, hiding facts at the end of sections
  (e.g. claim turnaround times) - relevant evidence is now shown in full (up to 1,600 chars per passage, 10k
  budget, low-relevance passages abbreviated); (3) truncated model output - max tokens 2048 -> 4096; (4) one
  unsupported extra sub-question blocking a cited answer - a planner answer citing verified evidence is now
  returned as ANSWERED_WITH_CAVEATS with the gaps listed (conflicts, missing user input and uncertain OCR keep
  their own outcomes). Added scripts/eval_retrieval.py + samples/golden_questions.json (20 answerable, 3
  out-of-scope) to measure recall/MRR per retrieval variant and calibrate the floor on the real models.
- 2026-10-28 (eval report on the real stack): hybrid retrieval R@3 = 1.0 (RRF MRR 0.95), but the reranker alone
  mis-ranked sections both retrievers put first (e.g. "what is covered": 0.014, rank 6), and irrelevant passages
  reached 0.13 at the 90th percentile, so no reranker threshold separates relevant from irrelevant. Changes: the
  final ranking is RRF over BM25, kNN and the reranker (reranker = third voter); a passage is relevant if the
  reranker scores it >= RELEVANCE_FLOOR or the fused ranking puts it in the top 3. Typed replies are stored as
  citable evidence (kind user, USER_STATED) and answers relying on them carry a caveat. A planner answer that
  cites verified evidence is returned with caveats even when some parts are MISSING (e.g. no X100 spec sheet),
  instead of refusing the whole comparison. Answers render Markdown tables; fullwidth 【e#】 citations accepted.
- 2026-10-28 (generalization review): the code changes of the last rounds are question-independent (fused ranking,
  rank-aware relevance, full evidence view, user statements as evidence, partial answers, scope check), but the
  evaluation was not: the 20-question set was mostly the failing questions, and the corpus had one keyword-stuffed
  phrase ("max flow rating"), now removed. Added a held-out set of 42 questions written per section and question type
  (never used for tuning) and scripts/eval_answers.py for end-to-end scoring (right outcome, required facts) per
  category. Policy from here: classify a failure, fix it at its level for all questions, verify on the held-out set.
  Known limits: the scope check only recognises code-like identifiers (X900, AQ-...), not unknown plain names;
  the relevance floor and top-3 rule are calibrated on this corpus and should be re-checked with eval_retrieval on a
  new one.
- 2026-10-28 (held-out results, 15 answers / 42 retrieval): retrieval R@3 0.95 (casual 0.67, all other categories
  1.0); answers 13/15 right in substance. Fixes by failure class: (a) outcome rules - a cited planner answer with
  no sub-questions (seen from the fallback model) was refused; the question itself now becomes the sub-question;
  (b) vocabulary gap in casual phrasing - initial search widened to 10 and the planner is told to re-search with
  document vocabulary when evidence is weak; (c) evaluation - fact matching normalises unicode spaces/dashes
  (two "wrong" answers were correct).
- 2026-10-28 (behaviour test pack): docs/behaviour_test_pack.md plus samples/make_test_uploads.py (clean, blurred and
  wrong-serial receipts, X300 warranty card, text-only installation certificate, conflicting purchase records,
  6-page scanned maintenance log, duplicate copy, unsupported CSV; Tesseract self-check). Two general fixes found
  while building it: (a) an identifier that appears only in an uploaded document (e.g. a serial on a card) stayed
  "unknown" after the document was read and forced a refusal - the scope check now re-runs after process_document
  and before finalizing; (b) an unsupported upload on a new question left an empty investigation behind - the file
  type is now checked before the investigation is created. The UI shows upload results (duplicate, OCR pages).
- 2026-10-28 (manual test run: 13b and 25). Failure classes and general fixes:
  (a) attached document ignored - the planner asked the user three times instead of reading the upload, then a
  re-run answered without reading it. Attachments are now read (indexed for the investigation, OCR only where
  needed) and searched before the first planner call; the planner still extracts specific fields itself.
  (b) unsupported answer accepted - "covered: the lease began 1 March 2025" cited passages that do not contain that
  date (it came from the catalog), and the amendment (12 months for commercial units) was never consulted. A
  pre-finalize review in code now sends an answer back (at most twice) when it states a date that is in no
  evidence and not derivable from one by a period the sources name, or when it relies on a document whose
  amendment (per `supersedes` metadata) was not consulted; a problem that survives becomes a caveat and the answer
  is never ANSWERED. Retrieval is version-aware: the first search also searches any amendment of a retrieved
  document, so the review rarely has to intervene. Planner rule 12: use values in their source's role.
  (c) slow tool failure - Elasticsearch client retries stacked on tool retries (~40 s); now no client retries plus a
  20 s circuit breaker, and a run whose first search fails with nothing else to use stops before any LLM call.
  (d) waiting on a quota that cannot recover soon - Groq's daily (TPD) limit returned "try again in 4m7s"; the
  client capped that to 60 s and waited 3 times (180 s). It now reads the real wait and fails at once when it
  exceeds LLM_MAX_WAIT_S (30 s), saying which quota and when it frees up. TOOL_FAILURE answers name the failed
  component. Also: indexing never narrows a global document to a session.
- 2026-10-28 (test 14 run inv_2ae678810782): the review sent an answer back twice for an invented lease date
  ("lease began 1 Mar 2025" - the contract's catalog effective date, not a purchase date), then a planner call hit a
  35 s per-minute wait (above the 30 s fail-fast cap), the run ended early, and the answer was rebuilt from the
  planner's SUPPORTED sub-questions - still "not covered". Fixes: (a) the final answer is checked whoever wrote it;
  a date no source contains withholds the answer (INSUFFICIENT_EVIDENCE) and the sub-questions resting on it are
  marked INSUFFICIENT - a caveat is not enough when the date decides the verdict; (b) LLM_MAX_WAIT_S default 65 s so
  per-minute limits (recover within a minute) are waited out and only multi-minute quotas fail fast.
  Not a flaw: an uploaded document is visible only to investigations it is attached to; re-attaching the same file
  shows DUPLICATE and reuses the already-processed document.
- 2026-10-29 (local model): gpt-oss:20b via Ollama chosen over Mistral Small 3.2 24B, Qwen 3.5 9B and Gemma 4 E4B:
  it fits a 16 GB GPU with the 12-16k context the planner needs (Mistral 24B does not), is the fastest (MoE, ~3.6B
  active), and is the model already exercised as the Groq fallback. LLM_PROVIDER=ollama implies the local URL, the
  model and no key; Ollama gets strict JSON-schema output (falls back to tool calling if the server ignores it),
  a 300 s timeout, a preload at startup, and check_llm verifies model downloaded / 100% on GPU / context >= 12k.
  eval_answers now writes one report per model and scripts/compare_models shows them side by side.
- 2026-10-29 (Ollama context): OLLAMA_CONTEXT_LENGTH set with setx was not picked up on the first try (ollama ps
  showed 4096), and the OpenAI-compatible endpoint cannot set num_ctx per request. scripts/setup_ollama creates a
  model variant with num_ctx baked in (gpt-oss:20b-16k, same weights, no extra disk), so the app no longer depends
  on a Windows environment variable; check_llm points to it when the loaded context is short.
- 2026-10-29 (local runs: malformed output, slow): two causes. (a) Action args were a free-form object, which strict
  mode can only express as a JSON string; the local gpt-oss:20b wrote "{}" or fragments into it ("Field required:
  question/doc_id", "':{' is not a dict"). Args are now a typed object (query, doc_id, question, ...), so the model
  fills named fields; this also helps Groq (its 20b fallback needed repairs). An ask_user without a question uses
  the stated reason. (b) Planner calls took 11-40 s locally vs ~2 s on Groq: the OpenAI-compatible endpoint
  cannot reliably set reasoning effort, context or keep-alive. LLM_PROVIDER=ollama now uses the native /api/chat
  with format=<schema> (grammar-constrained), think="low" for gpt-oss (off for other thinking models),
  options.num_ctx=16384 and keep_alive per request; check_llm prints prompt/output tokens and tokens/s.
- 2026-10-29 (local runs, round 2): typed args fixed the "Field required" errors, but gpt-oss through Ollama
  sometimes returned an EMPTY reply under grammar-constrained output (inv_bf45a1646ac6). The Ollama client now
  retries such a call once with the schema in the prompt (format=json) and extracts the JSON object - a different
  mechanism, so a different failure mode. temperature 0 + fixed seed for reproducible plans; num_predict 8192
  (hidden reasoning counts against it). A planner that fails before any decomposition is now TOOL_FAILURE
  ("model output unusable, not a lack of evidence") instead of "the documents do not contain it". Steps record
  prompt/output tokens (shown in the UI timeline) to locate local latency; the prompt asks for brief sub-questions.
- 2026-10-29 (test 15, inv_8f01cbe6976e): with the clean receipt the answer should be "covered" (bought 20-03-2025,
  commercial, 12 months -> 20-03-2026), but it was refused because the usage classification stayed UNVERIFIED. The
  extractor read 'COMMERCIAL' with the exact quote, but gave no page number, and grounding required one; the
  word itself was read at 96 (only the smudged signature on that page is low). Grounding now looks the quote up
  on every page of the document (the model's page is a hint), sets the page where it was found, and also
  rejects a value that is not inside its own quote. Trust still comes only from the page and OCR confidences.
- 2026-10-29 (inv_1636492bcd2e): the planner finalized citing only the scanned Schedule B passage (e7). A passage is
  UNVERIFIED when any word in it is low-confidence - here only the smudged signature (17), not "COMMERCIAL" (96) -
  so the guard held sq6 back and the answer was refused. Relying on the planner to call field extraction was not
  reliable. Before finalizing, the loop now re-reads every sub-question that is UNVERIFIED only because of OCR
  passages at field level (automatic process_document extract_only, code-grounded word by word). A clearly read
  claim becomes SUPPORTED and is cited; a genuinely uncertain value (smudged date) stays UNVERIFIED. The page-wide

- 2026-10-29 (OCR rework, inv_e8b2892f5f28 and inv_3d116fd6e884): verification moved from "quote" and "passage" level
  to the words a value is made of. (1) Field grounding (app/ingestion/ocr_verify.verify_value) finds the VALUE in
  the page's OCR words and requires each of those words >= threshold; the model's quote and page are only hints
  (copied [[?..]] markers, "(page 3)" or a missing page number had turned a value read at 96 into UNVERIFIED).
  (2) A sub-question citing a flagged OCR passage is checked in code against its own claim (check_claim): every
  value in the note (dates, numbers, codes, capitalised labels) must be a clearly read word of the passage, no
  claim word may be an uncertain word, word-level matching ('2025' does not match inside 'R-2025-04417'). This
  runs at every step without a model call; the LLM field re-read remains a fallback. The smudged signature no
  longer blocks "COMMERCIAL"; the smudged date (test 16) and blurred receipt (15) still refuse. Both real runs
  replay as ANSWERED. Planner rule 4 asks for the relied-on value in the note. Test sheet: renumbered to the
  revised 24 cases, cross-references and two upload paths fixed; interruption needs Ctrl+C twice (uvicorn waits
  for background work on the first); model-down test for Ollama = quit Ollama.
